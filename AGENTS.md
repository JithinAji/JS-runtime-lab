# Project Instructions

## Project Overview

This project is a JavaScript Runtime Lab designed to explore and explain JavaScript execution, execution contexts, the call stack, asynchronous execution, microtasks, tasks, and browser runtime behavior.

The goal is to develop a deeper understanding of JavaScript through experiments and practical implementation.

## Core Development Principles

- Understand the existing code before proposing changes.
- Keep changes small, focused, and easy to review.
- Avoid unnecessary abstractions, dependencies, and files.
- Do not expand the scope of a task without justification.
- Preserve existing behavior unless the task explicitly requires changing it.
- Do not rewrite working code merely to make it look different.

## Learning-First Workflow

- Prioritize helping the developer understand concepts over generating complete implementations.
- For learning tasks, explain the relevant concept and encourage experimentation before implementing a solution.
- When introducing an unfamiliar concept, explain why it is needed.
- Explain important implementation decisions and relevant trade-offs.
- Do not silently implement an entire feature when a smaller guided step would be more appropriate.

## Investigation Before Implementation

- Inspect the relevant code before suggesting changes.
- Identify the likely root cause before proposing a fix.
- Distinguish verified facts from assumptions.
- When investigating a bug, report findings before modifying code.
- Do not make unrelated changes while fixing a specific issue.

## Coding Conventions

- Follow the existing project conventions.
- Use meaningful variable and function names.
- Keep functions and responsibilities understandable.
- Use Prettier for consistent formatting.
- Avoid adding comments that merely repeat what the code already says.
- Prefer straightforward implementations over unnecessary abstractions.

## Testing and Verification

- Run relevant tests after making changes when tests are available.
- Verify behavior using the actual application when practical.
- Report which checks were run and whether they passed.
- Never claim that a test passed unless it was actually executed.
- Identify untested behavior and known limitations.

## Reporting Changes

After implementing a change, summarize:

1. What changed.
2. Why the change was necessary.
3. Important implementation decisions.
4. Tests or verification performed.
5. Any remaining limitations or concerns.
